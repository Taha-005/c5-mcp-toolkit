
# Reflection

The hardest design decision was where to draw the lines between the three tools. I applied the "and" test from class: whenever a description needed "and," that behavior belonged in the Orchestration tool rather than in the Data or Action tool. As a result, `save_plan` deliberately does not check the weather, and `get_weather_forecast` never writes anything. The one judgment call was geocoding: turning a city name into coordinates is technically a separate step, but I kept it inside the Data tool because it is never useful to the user on its own, and exposing it would add a fourth tool, an extra model round trip, and another point of failure. To keep the Orchestration tool from duplicating logic, I put all behavior in a plain `weather_core` module and made each MCP tool a thin wrapper, so `plan_outing` reuses the same functions the other two tools expose. Every predictable failure returns a coded error (for example `[CITY_NOT_FOUND]` or `[NO_SUITABLE_DAY]`) that the agent can explain instead of crashing or failing silently. Practical challenges included the latest `mcp` package (v2) renaming FastMCP, so I switched to the standalone `fastmcp` package, and Groq retiring my first model, so the model is now configurable in `.env` (I used `openai/gpt-oss-120b`). Testing also showed why tools matter: the model once called 9 November 2026 a Saturday when it is a Monday, so I added today's weekday to the agent's instructions; and when I asked it to save a plan in the past, it refused before calling the tool, which is why the server-side validation is verified by unit tests.

Three tools were enough for the core flow (look up, save, plan), and because they do not overlap, the agent chose between them correctly in every test query. The closest overlap is that both `save_plan` and `plan_outing` save, which I handled through explicit descriptions and agent instructions. The limit of three did show, though: I exposed saved plans as an MCP resource, but resources are application-controlled, so the agent cannot read them on its own, and "what have I saved?" would need a separate `list_plans` Data tool. As next steps, I would add `list_plans` and `delete_plan`, move the day-scoring logic into its own tool so the ranking can be reused and tested independently, implement orchestration as an agent-as-tool, and deploy the server remotely so other hosts can use it.
